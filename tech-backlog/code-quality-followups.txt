  1. Define a Global ApiResponse Type
  Create a dedicated file for API types (e.g., types/api.ts). This interface should handle both success and error states predictably.

    1 // types/api.ts
    2 export interface ApiResponse<T> {
    3   data: T | null;      // The actual payload (User, Habit, etc.)
    4   success: boolean;    // Quick check for the UI
    5   message?: string;    // Human-readable feedback (optional)
    6   error?: ApiError;    // Structured error details
    7 }
    8
    9 export interface ApiError {
   10   code: string;        // 'AUTH_EXPIRED', 'VALIDATION_ERROR', etc.
   11   message: string;     // Technical or user-facing message
   12   statusCode: number;  // HTTP status code (404, 500, etc.)
   13 }

  2. Implement a Response Transformer in apiConfig.ts
  Instead of manually wrapping the response in every service, use an Axios Interceptor. This centralizes the "Standardization" logic.

  How it works:
   * On Success: Extract the data and wrap it in your ApiResponse.
   * On Error: Catch the Axios error, parse the status code, and return a standardized ApiError object.

    1 // config/apiConfig.ts example logic
    2 apiClient.interceptors.response.use(
    3   (response) => {
    4     // Transform raw Axios response to ApiResponse<T>
    5     return {
    6       data: response.data,
    7       success: true,
    8       message: response.data?.message || 'Success',
    9     };
   10   },
   11   (error) => {
   12     // Transform Axios error to ApiResponse<null>
   13     const apiError = {
   14       data: null,
   15       success: false,
   16       error: {
   17         code: error.response?.data?.code || 'UNKNOWN_ERROR',
   18         message: error.response?.data?.message || error.message,
   19         statusCode: error.response?.status || 500,
   20       }
   21     };
   22     return Promise.resolve(apiError); // Return resolved so the service doesn't have to try/catch
   23   }
   24 );

  4. Implementation in Screens/Hooks
  In your UI, you no longer need to guess how to handle errors. The structure is always the same:

    1 const handleLogin = async () => {
    2   const result = await authService.signIn(creds);
    3
    4   if (!result.success) {
    5     // Always check .success first
    6     showToast(result.error?.message || 'Login failed');
    7     return;
    8   }
    9
   10   // TypeScript knows result.data is User here because of the generic <T>
   11   setUser(result.data);
   12 };

  Why this approach?
   1. Predictability: Every service returns the same object structure.
   2. Cleaner UI Code: You eliminate repetitive try/catch blocks in your components.
   3. Type Safety: Using ApiResponse<T> ensures that the data property is correctly typed for each specific feature (e.g., ApiResponse<Habit[]>).
   4. Error Centralization: If your backend changes its error format, you only update the interceptor in one file (apiConfig.ts).
